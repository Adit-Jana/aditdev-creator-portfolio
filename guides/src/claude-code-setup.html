01The 8 files that matter

Claude Code starts every session knowing nothing about you. These files are how it learns. Each one has a different reach.

FileWhat goes in itWho it applies to
~/.claude/CLAUDE.mdYour personal habits: language, style, how you like answersYou, every project
./CLAUDE.mdThe project: commands, architecture, standards. Commit it.Everyone on the repo
./CLAUDE.local.mdYour sandbox URLs, test accounts. Add to .gitignore.You, this project
.claude/rules/*.mdRules that only apply to some paths, like src/api/**Everyone, matching files only
.claude/settings.jsonPermissions, hooks, plugins, env vars. Commit it.Everyone on the repo
.claude/settings.local.jsonYour own overrides. Kept out of git.You, this project
.claude/skills/<name>/SKILL.mdRepeatable workflows you call with /nameEveryone (or ~/.claude/skills for you)
.claude/agents/<name>.mdSpecialist subagents, such as a code reviewerEveryone (or ~/.claude/agents for you)

Plus .mcp.json for shared tool connections (section 08). Run /status inside Claude Code to see which settings files loaded, and /memory to open the CLAUDE.md files in use.

The rule of thumbCLAUDE.md is where you write down what you would otherwise explain again every session. If you have said it twice, it belongs in a file.

02Your project CLAUDE.md

Start with /init. Claude reads the codebase and writes a first draft with the build commands, tests and conventions it finds. Then edit it down. The official guidance: keep each CLAUDE.md under about 200 lines, because a longer file takes more context and Claude follows it less closely.

Write rules you could check. "Run pnpm test before you say a task is done" works. "Write good tests" does not.

CLAUDE.md
# Project: Orders API
Node 22 + Fastify + Postgres (Prisma). Monorepo with pnpm workspaces.

## Commands
- Install: pnpm install
- Dev server: pnpm dev            (http://localhost:3000)
- Tests: pnpm test                (run before saying any task is done)
- One test: pnpm test -- orders.spec.ts
- Lint + types: pnpm lint && pnpm typecheck

## Architecture
- apps/api       HTTP routes only. No business logic here.
- packages/core  Business logic. Pure functions, fully tested.
- packages/db    Prisma schema and migrations. Never edit generated files.

## Standards
- TypeScript strict. No `any`. Prefer named exports.
- Every new endpoint: zod input schema + a test in the same PR.
- Errors: throw AppError(code, message). Never return raw stack traces.

## Never
- Never run migrations against production. Use pnpm db:migrate:dev only.
- Never commit .env files or print secrets in logs.

## How I work
- For changes over ~50 lines, show a plan first and wait for my OK.
- Small commits with clear messages. Do not push unless I ask.

@docs/architecture.md

The last line is an import: @path/to/file pulls that file into context alongside the CLAUDE.md. Use it to point at docs you already maintain instead of copying them.

03Your personal CLAUDE.md

~/.claude/CLAUDE.md loads in every project on your machine. Put only things that are true everywhere.

~/.claude/CLAUDE.md
# About me
Backend developer, 4 years. Main stack: TypeScript, Python, Postgres.

# How to answer
- Lead with the answer, then the reason. Keep it short.
- When you change code, show only the changed lines plus 2 lines of context.
- If a request is ambiguous, ask one question before writing code.

# Habits
- Read the existing code before adding a new helper. Reuse what exists.
- Run the tests you touched. Say clearly if you could not run them.
- Never use `git push --force` or delete branches without asking.

04Rules for parts of the code

When a rule only matters for some files, put it in .claude/rules/ with a paths list. Claude only loads it while working on matching files, so your main CLAUDE.md stays short.

.claude/rules/api.md
---
paths:
  - "apps/api/**/*.ts"
---
# API rules
- Every route validates input with a zod schema.
- Every route has a test in apps/api/test that covers a 400 case.
- Return { data } on success and { error: { code, message } } on failure.
.claude/rules/frontend.md
---
paths:
  - "apps/web/**/*.tsx"
---
- Use components from packages/ui before writing new ones.
- No inline colours. Use the tokens in packages/ui/tokens.ts.

05Permissions and hooks

CLAUDE.md is advice. Settings are enforced. Use .claude/settings.json to allow the safe commands you run all day (fewer prompts) and to block what must never happen.

.claude/settings.json
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [
      "Bash(pnpm test *)",
      "Bash(pnpm lint)",
      "Bash(pnpm typecheck)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Bash(git push *)"
    ]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "jq -r '.tool_input.file_path' | xargs pnpm prettier --write --log-level warn" }
        ]
      }
    ]
  }
}

Hooks are shell commands Claude Code runs at fixed moments, every time, no matter what the model decides. The events you will use most:

EventRunsGood for
PreToolUseBefore a tool callBlocking risky commands or edits to protected files
PostToolUseAfter a tool callFormatting, linting or type-checking after every edit
UserPromptSubmitWhen you send a messageAdding context, such as the current branch or ticket
SessionStartWhen a session opensLoading project status or recent changes
StopWhen Claude finishes a replyRunning tests, sending a notification
CarefulA hook runs with your user's permissions. Read any hook before you add it, and keep project hooks in the committed settings so the team can review them.

06Your own skills

A skill is a folder with a SKILL.md. Claude loads it when the description matches the task, or you call it with /skill-name. Use skills for workflows you repeat: shipping a PR, adding an endpoint, writing a migration.

.claude/skills/new-endpoint/SKILL.md
---
name: new-endpoint
description: Add a new REST endpoint to apps/api with schema, handler, test and docs. Use when asked to add or create an API route.
---
# Add an endpoint
1. Ask for: method, path, input fields, response shape, auth rule.
2. Write the zod schema in apps/api/schemas/<name>.ts.
3. Put business logic in packages/core, not in the route.
4. Add the route in apps/api/routes and register it in routes/index.ts.
5. Write tests: one success case and one 400 case.
6. Run pnpm test -- <name> and pnpm typecheck. Fix until both pass.
7. Add the endpoint to docs/api.md.
8. Reply with the files changed and the test output.
TipAdd disable-model-invocation: true to the frontmatter for skills that should only run when you type the command, such as /deploy. Skills can also hold scripts and templates in the same folder.

07A reviewer subagent

Subagents run in their own context window, so a long review does not fill your main chat. Save this file and ask "use the code-reviewer on my changes".

.claude/agents/code-reviewer.md
---
name: code-reviewer
description: Reviews the current git diff for bugs, security issues and missing tests. Use after finishing a change and before committing.
tools: Read, Grep, Glob, Bash
---
You are a senior reviewer. Run `git diff` and review only what changed.
Report findings as: file:line, severity (high/medium/low), the problem, the fix.
Check: wrong logic, unhandled errors, secrets in code, missing input validation,
missing or weak tests. Skip style nits. If nothing is wrong, say so in one line.

08MCP: connect your tools

MCP servers give Claude access to tools outside your repo: GitHub, your database, Sentry, Notion, a browser. Add one from the terminal:

claude mcp add --transport http notion https://mcp.notion.com/mcp

To share a server with the team, put it in .mcp.json at the repo root and commit it. Teammates are asked to approve project servers the first time.

.mcp.json
{
  "mcpServers": {
    "notion": { "type": "http", "url": "https://mcp.notion.com/mcp" }
  }
}

Only add servers you trust. An MCP server can read what you give it and act with the access you grant.

09The daily workflow

MomentDo this
Big or unclear taskSwitch to plan mode (Shift+Tab). Let Claude read and propose a plan. Approve, then build.
New, unrelated task/clear. Old context from the last task only gets in the way.
Long session/context to see what fills the window. /compact to summarise and keep going.
Before "done"Ask Claude to run the tests and show the output. Proof, not promises.
Two tasks at onceUse git worktrees so each Claude session has its own copy of the repo.
Claude repeats a mistakeFix it once, then add a line to CLAUDE.md so it never comes back.

10The master setup prompt

Open Claude Code in your repo and paste this. It does most of this guide for you, then you review.

Set this repository up for Claude Code. Work in this order and stop for my
approval after step 2.

1. Read the repo: package files, README, CI config, folder structure, tests.
2. Show me a plan listing every file you will create, with one line on each.
3. Create ./CLAUDE.md under 150 lines with: one-paragraph overview, exact
   commands (install, dev, test, single test, lint, typecheck, build),
   architecture map of the top folders, coding standards you can see in the
   code, a "Never" list, and my workflow: plan first for big changes, run
   tests before saying done, small commits, never push without asking.
4. Create .claude/rules/ files for any area with its own conventions
   (API, frontend, database, infra), each with a paths: list.
5. Create .claude/settings.json: allow the safe read-only and test commands
   you found, deny reading .env files and git push.
6. Create .claude/agents/code-reviewer.md that reviews the git diff for
   bugs, security issues and missing tests.
7. Create one skill in .claude/skills/ for the most repeated task in this
   repo (for example adding an endpoint, a component or a migration).
8. Add CLAUDE.local.md and .claude/settings.local.json to .gitignore.
9. Report what you created and anything you were unsure about.

Setup checklist

  • /init run, then trimmed to under 200 lines
  • Every command in CLAUDE.md copied from a real script and tested
  • A "Never" list for the things that would hurt
  • Path rules for areas with their own conventions
  • .claude/settings.json committed with allow and deny rules
  • A format or lint hook after edits
  • One skill for your most repeated task
  • A reviewer subagent
  • CLAUDE.local.md and settings.local.json in .gitignore
